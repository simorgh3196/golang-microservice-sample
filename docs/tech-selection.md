## 1. 内部RPC通信プロトコル

マイクロサービス間の高速・型安全な内部通信プロトコルの選定。

| 候補技術 | メリット | デメリット / 懸念点 | 総合評価 |
| :--- | :--- | :--- | :---: |
| **Connect-RPC**<br>*(採用)* | ・HTTP/2 (gRPC互換) と HTTP/1.1 (JSON) を両サポート<br>・ブラウザから直接呼べる（gRPC-Web不要）<br>・Bufエコシステムによる優れたコード生成と後方互換性チェック | ・純粋なgRPCより歴史が浅い（ただし急速にデファクト化中） | **◎ 最適** |
| **Pure gRPC** | ・圧倒的な本番実績と全プログラミング言語のサポート<br>・Protobufによる高速バイナリシリアライズ | ・ブラウザ直接通信に Envoy (gRPC-Web) が必須<br>・curlでのアドホックなデバッグが困難 | ◯ |
| **REST (JSON/HTTP)** | ・誰でも知っており、汎用HTTPクライアントで叩ける | ・型安全性がない（スキーマの強制力が弱い）<br>・JSONパースのオーバーヘッド | △ |

### 💡 採否の理由
内部マイクロサービス間通信には型安全性とHTTP/2の多重化性能が必須。Connect-RPCはgRPCの利点をすべて持ちつつ、curlやブラウザからも透過的に呼べるため、開発者体験（DX）と本番性能のバランスが最も優れている。

## 2. BFF / API Gateway

自社フロントエンド（Web/Mobile）向けのデータ集約・最適化レイヤーの選定。

| 候補技術 | メリット | デメリット / 懸念点 | 総合評価 |
| :--- | :--- | :--- | :---: |
| **GraphQL (gqlgen)**<br>*(採用)* | ・フロントが必要なデータだけを取得（Over-fetching防止）<br>・スキーマ駆動（Schema-First）でTypeScript型自動生成と直結<br>・**DataLoaderによるN+1クエリ解消**の実践に最適 | ・キャッシュ設計がやや複雑<br>・悪意のあるネストクエリ（DoS）への複雑度制限が必要 | **◎ 最適** |
| **REST BFF** | ・HTTPキャッシュ（ETag, Cache-Control）が素直に効く<br>・実装がシンプル | ・画面ごとに専用エンドポイントが増殖し、肥大化しやすい<br>・複数画面の要求を満たすために過剰取得が発生 | ◯ |
| **gRPC-Gateway** | ・ProtobufからRESTリバースプロキシを自動生成 | ・フロントエンド固有の集約・加工ロジックを柔軟に挟みにくい | △ |

### 💡 採否の理由
マルチテナントSaaSでは画面によって要求されるデータの深さ・粒度が異なる。GraphQLを採用し、DataLoaderやクエリ深度制限を組み込むことで、高効率かつ安全なBFFを実現できる。

## 3. データベース & マルチテナント分離戦略

マルチテナントにおけるデータ分離（アイソレーション）とDBエンジンの選定。

| 候補技術 | 特徴・マルチテナントでの強み | 懸念点・コスト | 総合評価 |
| :--- | :--- | :--- | :---: |
| **PostgreSQL (RLS)**<br>*(標準採用)* | ・**Row Level Security (RLS)** によるDB層での強制的な行レベル分離<br>・強固なACIDトランザクション、豊富なエコシステム（`pgx`, `sqlc`, `pgvector`） | ・超巨大テナント時の水平スケールには工夫が必要 | **◎ 最適<br>(コアDB)** |
| **Turso (libSQL)**<br>*(比較検証)* | ・SQLiteベースのエッジ分散DB<br>・**Database-per-Tenant**（テナント毎にDBファイルを分ける超分離）が超安価に実現可能 | ・クロスデータベースの集計クエリが難しい | **◯<br>(エッジ/特定テナント)** |
| **TiDB (Serverless)**<br>*(比較検証)* | ・分散NewSQL（水平スケーラブル、MySQL互換）<br>・HTAP対応（トランザクションと大規模分析クエリの同時処理） | ・ローカル単体起動がやや重い（クラウド無料枠向き） | **◯<br>(分析/大規模テナント)** |
| **MongoDB / DynamoDB** | ・スキーマレスで柔軟なJSON保存 | ・リレーショナルな権限管理やRLSの仕組みを自前実装する必要がある | △ |

### 💡 採否の理由
基本方針として最も実績豊富でRLSによる確実なデータ分離が可能な **PostgreSQL** をコアに採用。特定要件（エッジ分散、大規模分析）の比較検証として **Turso / TiDB** をサービスごとに組み合わせるポリグロット・パーシステンス構成をとる。

## 4. 非同期メッセージング & イベントバス

マイクロサービス間の疎結合化・通知配信・Outboxパターンを支えるイベント基盤。

| 候補技術 | メリット | デメリット / 懸念点 | 総合評価 |
| :--- | :--- | :--- | :---: |
| **NATS / Redis Streams**<br>*(採用)* | ・超軽量（メモリ数MB〜数十MB）でローカルk8s環境で瞬時に起動<br>・Goとの親和性が極めて高い<br>・Pub/Sub、Queue Group（ロードバランス）、At-least-once配信を完全網羅 | ・数テラバイト規模の永続ストリーム保存にはKafkaに軍配 | **◎ 最適** |
| **Apache Kafka** | ・金融・ビッグデータ規模の分散コミットログ業界標準 | ・運用・構築が非常に重厚（JVM、大量メモリ、KRaft/ZooKeeper）<br>・ローカル学習環境を圧迫 | △ |
| **RabbitMQ** | ・高度なルーティング（Topic/Exchange）機能 | ・NATSに比べてメモリフットプリントと運用難易度が高い | ◯ |

### 💡 採否の理由
ローカルKubernetes環境で軽快に動作し、かつ「Transactional Outbox」「Dead Letter Queue (DLQ)」「コンシューマーグループ」の本質を100%実践・学習できる **NATS / Redis Streams** が最適。

## 5. 認証・認可基盤

マルチテナントSaaSにおけるAuthN / AuthZのアーキテクチャおよび「Cookie vs JWT 論争」への対応。

### 🚨 「ブラウザセッションにJWTを使ってはいけない」問題へのアプローチ
近年指摘される「JWT is bad for sessions」の課題（①即時失効/BANができない、②XSSによるトークン盗難、③権限変更の反映遅延、④サイズ肥大化）を受け、本システムでは**外側と内側で技術を使い分ける「BFFハイブリッド認証パターン」**を採用します。

| 境界レイヤー | 採用技術 | 目的・選定理由 |
| :--- | :--- | :--- |
| **外側（ブラウザ ⇔ BFF）** | **HttpOnly Cookie (Session ID)** | **最高レベルの安全性**: JSから参照不可（XSS耐性）、ログアウト/BAN時にRedisからセッション削除で即時失効。 |
| **内側（BFF ⇔ マイクロサービス）** | **短命な内部JWT (有効期限1分) / メタデータ伝播** | **最高レベルの性能**: 内部サービスが毎回AuthDB/Redisに問い合わせず、公開鍵検証だけでステートレスに水平スケール。 |
| **外部連携（API Key / OAuth2）** | **ハッシュ化 API Key (SHA-256) & JWT** | **外部エコシステム標準**: サードパーティやAIエージェント向けのセキュアなスコープ認可。 |

### 🛠 認証基盤の実装方式の比較

| 候補アプローチ | メリット | デメリット / トレードオフ | 総合評価 |
| :--- | :--- | :--- | :---: |
| **自前Go実装 (Session Cookie + 内部短命JWT + RLS)**<br>*(採用)* | ・セッション管理、短命JWT署名・公開鍵検証、コンテキスト伝播、RLS連携の**内部メカニズムを完全に理解・掌握できる**<br>・外部依存ゼロで超高速 | ・2FA/WebAuthn等を本番フル実装する場合は工数が大 | **◎ 最適<br>(学習・掌握)** |
| **Go製OSS (Zitadel / Ory Kratos)** | ・マルチテナント・OIDCが組み込み済みの高品質OSS | ・設定項目が多く、内部の仕組みがブラックボックス化しやすい | ◯ |
| **SaaS (Auth0 / Clerk)** | ・UI付きで即日導入可能 | ・クラウド費用・外部APIコール依存が発生し、ローカル閉塞環境で動かしにくい | ◯ |

### 💡 採否の理由
「ブラウザの安全なセッション管理（Cookie）」と「マイクロサービスの高速な分散検証（短命JWT）」の長所を融合した**BFFハイブリッド認証**を自前実装することで、実務で最も堅牢な認証認可アーキテクチャを体得する。

## 6. 主キー・分散ID生成

データベースの主キー（Primary Key）の選定。

| 方式 | 構造 | B-treeインデックス効率 | 時系列ソート | 採否 |
| :--- | :--- | :---: | :---: | :---: |
| **UUIDv7** | 48bitタイムスタンプ + 74bit乱数 (128bit) | **◎ 最高の局所性** | **◯ 可能** | **採用** |
| **ULID** | 48bitタイムスタンプ + 80bit乱数 (Base32) | ◎ 良好 | ◯ 可能 | ◯ |
| **UUIDv4** | 完全ランダム (128bit) | **✕ 挿入ごとに断片化 (ページ割れ多発)** | ✕ 不可 | ✕ 不採用 |
| **Auto-Increment (BIGINT)** | 連番整数 (64bit) | ◎ 良好 | ◯ 可能 | ✕ 分散時衝突・推測リスク |

### 💡 採否の理由
`UUIDv4` はランダムなため、データ量が増えるとDBのB-treeインデックスが断片化（ページ割れ）を起こし挿入性能が急激に劣化する。**`UUIDv7`** はタイムスタンプ順に並ぶため、B-treeの末尾に綺麗に挿入され、**連番整数の挿入性能とUUIDの分散一意性を両立できる**ため採用。

## 7. ローカル実行環境 & IaC

開発環境およびインフラコード管理手法の選定。

| 方式 | 構成 | メリット | デメリット / トレードオフ | 採否 |
| :--- | :--- | :--- | :--- | :---: |
| **k3d (軽量k8s) + Kustomize + Terraform** | Docker上の軽量K8s | ・本番と同じKubernetesマニフェスト（Ingress, Service, HPA, Secret）を完全無料で実行可能<br>・クラウド無料枠連携をTerraformでコード化 | ・Docker Compose単体より初期の概念理解が必要 | **採用** |
| **Docker Compose 単体** | 複数コンテナ一括起動 | ・最も手軽で学習コストが低い | ・Service Mesh, Ingress Routing, HPA, Rolling Updateなどの本番k8s運用技術が学べない | ◯ (補助) |

### 💡 採否の理由
実務のシニアバックエンド開発ではKubernetesとIaCの理解が不可欠。`k3d` を採用することで、**「PC1台・無料」でありながら本番クラウド（EKS/GKE）と全く同じKubernetes運用・IaCを体得できる**環境を実現する。

## 8. ベクトル検索 & ナレッジストレージ (RAG)

マルチテナントAIエージェント基盤におけるベクトル類似度検索エンジンの選定。

| 候補技術 | メリット | デメリット / 懸念点 | 総合評価 |
| :--- | :--- | :--- | :---: |
| **PostgreSQL (RLS + pgvector)**<br>*(標準採用)* | ・**RLSによる他テナントデータの完全物理遮断**<br>・**ACIDトランザクション（Dual Write問題ゼロ）**: ドキュメント更新とベクトル更新を1コミットで原子化<br>・**ハイブリッド検索 (RRF)**: `tsvector` (BM25キーワード) と `pgvector` をSQL単体で合成 | ・億単位の超大規模ベクトルではインデックスメモリ消費に注意 | **◎ 最適<br>(コアRAG)** |
| **専用ベクトルDB (Qdrant / Milvus)**<br>*(比較検証)* | ・Rust/C++製で極限の低レイテンシ・億単位ベクトルの高速検索<br>・リッチなPayloadメタデータフィルタ | ・RDBMSとの二重管理（Dual Write）によるデータの不整合リスク<br>・別サーバーの運用コスト | **◯<br>(超大規模)** |
| **フルマネージドSaaS (Pinecone)** | ・インフラ運用完全不要 | ・外部SaaS依存・課金発生、ローカル閉塞環境で動かしにくい | △ |

### 💡 採否の理由
企業向けSaaSでは「他テナントへのデータ漏洩防止」と「ドキュメント更新時の即時データ整合性（ACID）」が最重要。PostgreSQL RLS + `pgvector` はこの2大要件を完璧に満たし、追加のインフラ費用もゼロで運用できるためコアに採用。

## 9. AIエージェント自律思考ループ & SDK選定

エージェントの推論ループ（ReAct / Plan-and-Execute）およびLLM連携の実装方式。

| 候補アプローチ | メリット | デメリット / トレードオフ | 総合評価 |
| :--- | :--- | :--- | :---: |
| **自前軽量ReActループ + 公式SDK**<br>*(採用)* | ・プロンプト構築、ツール呼び出し（Tool Calling）、コンテキスト要約、リトライの**内部挙動を100%制御・掌握できる**<br>・余計な依存がなくGo本来の超高速・低メモリで動作 | ・基本のループ制御コード（数十行）を自作する必要がある | **◎ 最適<br>(学習・掌握)** |
| **LangChainGo** | ・コンポーネントが用意されている | ・Go界隈でのメンテナンス更新が遅れがち<br>・抽象化が過剰で内部がブラックボックス化し、障害解析が困難 | △ |

### 💡 採否の理由
Goのマイクロサービスでは、過度なラッパーフレームワークに頼らず、プロンプトの動的合成・Tool Callディスパッチ・Connect-RPCストリーミング配信の**本質的なパイプラインを自前実装することで真のアーキテクチャ力を体得する**。

## 10. リアルタイム思考ストリーミング (BFF ⇔ フロント)

エージェントの思考過程・ツール実行状況・生成トークンのリアルタイム配信プロトコル。

| 候補技術 | メリット | デメリット / トレードオフ | 総合評価 |
| :--- | :--- | :--- | :---: |
| **Server-Sent Events (SSE)**<br>*(採用)* | ・**HTTP/2 ネイティブ**: 単一コネクションで多重化、プロキシ/LBと高相性<br>・**Vercel AI SDK (`useChat`) と標準で直結可能**<br>・切断時の自動再接続がブラウザ標準組み込み | ・単方向（サーバー ➔ クライアント）のみ（エージェント配信には十分） | **◎ 最適** |
| **GraphQL Subscription (WS)** | ・GraphQLスキーマに統合可能 | ・ステートフルなWebSocket接続維持がk8sでの負荷・再接続管理を複雑化 | ◯ |
| **Long Polling** | ・古いブラウザでも動作 | ・リクエスト数が爆発し非効率 | ✕ |

### 💡 採否の理由
エージェントのストリーミングは「サーバーからクライアントへの単方向プッシュ」であり、HTTP/2と抜群に相性が良く、フロントエンド標準（Vercel AI SDK等）とも即座に繋がる **SSE** を採用。

## 11. キャッシュ & 分散データストア (Valkey / Redis)

Redisのライセンス変更（RSALv2/SSPL）に伴う選定方針。

- **採用方針**: **Valkey / Redis (完全互換)**
- **選定理由**: Linux Foundation傘下の完全オープンソースフォークである **Valkey** を視野に入れつつ、Goの標準クライアント（`go-redis`）を用いて実装。ローカルDockerでは互換イメージ（`valkey/valkey` または `redis:alpine`）のいずれもシームレスに差し替え可能。

## 12. 外部連携 API プロトコル (OpenAI 互換 vs 独自 REST vs gRPC)

サードパーティ開発者・CI/CD・外部AIツール向けの外部公開インターフェースの選定。

| 候補アプローチ | メリット | デメリット / トレードオフ | 総合評価 |
| :--- | :--- | :--- | :---: |
| **OpenAI 互換 REST (`/v1/chat/completions`) ＋ 管理用REST**<br>*(採用)* | ・**世界中のエコシステムと即座に統合可能**（Cursor, Continue, Cline, Python/TS `openai` SDK, LangChain）<br>・`base_url` と API Key を渡すだけで、自作SDKなしで利用可能<br>・裏側でRLS・企業規約・RAGを透過的に自動注入できる | ・OpenAI互換ストリーミング（SSE）のチャンク形式に合わせたレスポンス変換が必要 | **◎ 最適** |
| **完全独自仕様 REST API** | ・自社のデータ構造に完全に一致させられる | ・外部ツール（Cursor等）から使うために専用プラグインやカスタムラッパーの開発・保守が必要 | △ |
| **外部向け gRPC / Connect-RPC** | ・バイナリ通信で極めて高速 | ・外部開発者が利用する際の導入障壁（Protobuf定義の配布・環境構築）が高い | ◯ (社内連携向き) |

### 💡 採否の理由
AIエージェントプラットフォームにおける最大のキラー機能は「既存のAI開発ツール（CursorやPythonスクリプト）から即座に叩けること」。対話・推論APIにデファクト標準の **OpenAI互換インターフェース** を採用し、管理APIには **シンプルなOpenAPI準拠REST** を組み合わせる構成が最も実務価値が高い。
